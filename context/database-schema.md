# database-schema.md

# Part 1 — Foundation

# Overview

## Purpose

The Sheybi database is the permanent source of truth for every piece of data generated by the platform.

It stores user identities, prediction markets, financial records, positions, wallets, administrator actions, notifications, and historical records.

The database is responsible for preserving all business data required for the platform to function correctly.

The database does not determine prediction market behaviour. That responsibility belongs exclusively to the Prediction Engine. The database only stores the results of validated business operations.

Every financial event recorded within the database must remain permanently traceable.

Every record must have one clearly defined owner, one purpose, and one lifecycle.

No entity may exist without a clearly defined responsibility.

---

# Responsibilities

The database is responsible for:

- Persisting all application data.
- Maintaining relationships between entities.
- Storing immutable financial history.
- Preserving user ownership.
- Supporting realtime synchronization.
- Supporting administrator auditing.
- Providing data required by the Prediction Engine.
- Providing historical records for reporting.
- Enforcing data integrity.

The database is not responsible for:

- Pricing prediction markets.
- Calculating probabilities.
- Executing settlement logic.
- Authenticating users.
- Processing payments.
- Rendering the user interface.

Those responsibilities belong to other architectural layers.

---

# Design Principles

The database must always satisfy the following principles.

## Single Source of Truth

Every piece of business information must exist in exactly one authoritative location.

Duplicate copies of financial information are forbidden unless explicitly required for auditing or performance.

---

## Referential Integrity

Every relationship between records must remain valid.

Child records cannot exist without their required parent records.

Relationships must never become orphaned.

---

## Explicit Ownership

Every record must have one clearly defined owner.

Ownership determines who may view, update or administer the record.

---

## Immutable Financial History

Financial history must never be edited or deleted.

Corrections must always create new records rather than modifying historical records.

---

## Auditability

Every administrative action affecting users, markets or finances must produce a permanent audit record.

Audit records are immutable.

---

## Deterministic Data

The same business event must always produce the same database changes.

Identical operations must never create different data structures.

---

## Separation of Concerns

Each table owns one responsibility.

Tables must never overlap responsibilities.

---

## Minimal Duplication

Data must not be copied between tables unless required for:

- Historical snapshots
- Performance optimization
- Regulatory compliance
- Auditing

---

## Predictable Relationships

Every relationship between entities must be explicitly documented.

Implicit ownership is forbidden.

---

## Financial Integrity

Every financial movement must be traceable from beginning to end.

Every movement must have:

- Origin
- Destination
- Amount
- Timestamp
- Reason

---

## Ledger

### Purpose

Stores the immutable financial history of the platform.

Every financial event creates exactly one Ledger record.

The Ledger is the legal accounting history of Sheybi.

---

### Ownership

System owned.

Users may view only their own related entries.

Administrators may view every entry.

---

### Fields

| Field | Type | Required | Description | Default |
|--------|------|----------|-------------|---------|
| id | UUID | Yes | Ledger identifier | Generated |
| sourceAccountId | UUID | Yes | Debit leg (origin / user wallet / platform account) | None |
| destinationAccountId | UUID | Yes | Credit leg (destination / user wallet / platform fee account) | None |
| userId | UUID | Optional | Related user | Null |
| walletId | UUID | Optional | Related wallet | Null |
| eventType | Enum | Yes | Financial event type | None |
| debit | Decimal(18,4) | Yes | Debit amount leaving source leg | 0.0000 |
| credit | Decimal(18,4) | Yes | Credit amount entering destination leg | 0.0000 |
| currency | String | Yes | ISO currency code | NGN |
| idempotencyKey | String | Yes | Unique idempotency reference key for balanced transaction | None |
| balanceAfter | Decimal(18,4) | Yes | Wallet balance after event | None |
| referenceId | UUID | Optional | Related business record | Null |
| description | String | Yes | Human-readable explanation | None |
| createdAt | DateTime | Yes | Record timestamp | Current Time |

*Double-Entry Accounting Rule*: Every ledger entry represents a balanced journal transaction where the debit leg equals the credit leg across identified origin, destination, and platform/fee accounts, bound by currency and a unique idempotency key.

---

### Relationships

May reference:

- Deposits
- Withdrawals
- Positions
- Markets
- Settlement

---

### Lifecycle

Created automatically.

Never edited.

Never deleted.

Immutable forever.

## Purpose

### Ownership

### Fields

| Field | Type | Required | Description | Default |

| updatedAt | DateTime | Yes | Last modification | Current Time |

*Single-Outcome Exposure Invariant (Database Constraint & Transactional Rule)*:
- Database Constraint: A Partial Unique Index `CREATE UNIQUE INDEX idx_active_user_market_position ON Position (userId, marketId) WHERE state IN ('Open', 'Partially Sold')` enforces that a user can have at most one active position record per market.
- Transactional Rule: Keyed by `userId` and `marketId`, the prediction engine enforces that buying an outcome when the user holds an active position in another option of the same market is atomically rejected before any funds or shares are updated.

### Relationships

Belongs to one User.

Belongs to one Market.

Belongs to one Market Option.

Has many Position History records.

### Lifecycle

Created after first purchase.

Updated after buys, sells and settlement.

Never physically deleted.

*PII & Bank Data Protection Rules*:
- Field-Level Encryption: `bankName`, `accountName`, and `accountNumber` are protected using AES-256 field-level encryption / tokenization at rest.
- Masked Display: API endpoints and UI components expose only masked values (e.g. `****1234`), revealing unmasked data exclusively to authorized payout processing services.
- Least-Privilege RBAC & Audit Logging: Decrypting bank account details requires dedicated administrative permissions, with every view or decrypt event logged to an immutable security audit log.
- Retention & Anonymization: Protected bank details are automatically anonymized or purged 90 days after withdrawal completion or account deletion.

### Relationships

Belongs to one Wallet.

Belongs to one User.

Creates Wallet Transaction.

Creates Ledger Entry.

May create Audit Log.

### Lifecycle

Created after successful validation.

Cannot be modified by the user after submission.

Moves through workflow until Paid or Rejected.

Never deleted.

# Financial Data

Financial information is intentionally separated from user profile information.

Stores only the user's current balances.

- Locked Balance
- Lifetime Deposits
- Lifetime Withdrawals
- Lifetime Profit

Stores immutable accounting history.

## Wallet Transactions

Stores user-friendly transaction history.

Designed for statements and account history.

---

## Deposits

Stores incoming money.

Never stores wallet balances directly.

---

## Withdrawal Requests

Stores outgoing money.

Tracks workflow until completion.

---

## Trading Fees

Trading fees are recorded inside Ledger and Wallet Transactions.

Fee amount is stored permanently.

Current MVP Fee

- 2.5% Buy
- 2.5% Sell

---

## Withdrawal Fees

Stored with every Withdrawal Request.

Current MVP Fee Policy:

- 2.5% Rate
- Minimum ₦150
- No maximum cap or upper limit
- Net Withdrawal Amount = Gross Amount - Math.max(150, Gross Amount * 0.025)

# Database Invariants

The following rules are mandatory.

The database must never violate these rules.

## Identity Rules

- Every User must own exactly one User Profile.
- Every User must own exactly one Wallet.
- Every Wallet belongs to exactly one User.
- Every User Profile belongs to exactly one User.

---

## Market Rules

- Every Market belongs to exactly one Category.
- Every Binary Market contains exactly two Market Options (YES and NO).
- Every Multi-Option Market contains at least three Market Options; creating or assigning a multi-option variant with fewer than three options is rejected.
- Every Market Option belongs to exactly one Market.
- Every Market has exactly one current Market State.
- A Resolved Market must have exactly one Winning Option.
- A Cancelled Market cannot later become Resolved.
- Liquidity assigned during Market creation cannot change after the Market enters the Open state.

---

## Position Rules

- Every Position belongs to exactly one User.
- Every Position belongs to exactly one Market.
- Every Position belongs to exactly one Market Option.
- Shares cannot exist without a Position.
- Shares owned cannot become negative.
- A Won Position cannot later become Lost.
- A Settled Position cannot return to an Open state.

---

## Financial Rules

- Every Wallet belongs to exactly one User.
- Wallet balances cannot become negative.
- Every Deposit belongs to exactly one Wallet.
- Every Withdrawal Request belongs to exactly one Wallet.
- Every successful Deposit creates one Wallet Transaction.
- Every successful Withdrawal creates one Wallet Transaction.
- Every successful Buy creates one Wallet Transaction.
- Every successful Sell creates one Wallet Transaction.
- Every successful Settlement creates one Wallet Transaction.

---

## Ledger Rules

- Every financial mutation creates exactly one Ledger Entry.
- Ledger Entries are immutable.
- Ledger Entries cannot be deleted.
- Ledger Entries cannot be reassigned.
- Every Ledger Entry must reference its originating business event.

---

## Audit Rules

- Every administrative action creates one Audit Log.
- Audit Logs are immutable.
- Audit Logs cannot be deleted.
- Audit Logs always record the acting administrator.

---

## Notification Rules

- Every Notification belongs to exactly one User.
- Notifications may transition only from Unread → Read → Archived.
- Archived Notifications remain queryable.

---

## Storage Rules

- Binary files must never be stored inside database records.
- The database stores only references to uploaded files.
- Financial history must never be stored inside cached systems.
- Cached data must never become the source of truth.
